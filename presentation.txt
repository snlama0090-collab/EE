================================================================================
WATTPULSE — EV CHARGING STATION FINDER
Presentation Summary / Speaker Notes
================================================================================

--------------------------------------------------------------------------------
1. PROJECT OVERVIEW
--------------------------------------------------------------------------------

What it is:
  WattPulse is a full-stack web application for finding, booking, and managing
  EV charging stations. It works as a marketplace: drivers search for nearby
  chargers on an interactive map, reserve one, and pay to charge their vehicle;
  station owners register and manage their chargers; admins moderate the
  platform.

Who it's for:
  - DRIVERS  — find nearby stations, book a charger, start/stop a charging
               session, track live countdowns, view receipts.
  - STATION OWNERS — register stations, manage charger status, monitor
               bookings and revenue, view analytics.
  - ADMINS   — approve/reject stations, manage users and reviews, view
               platform-wide reports.

Tech stack (as actually implemented):
  - Backend:  PHP 8.x (vanilla, no framework) with PDO
  - Database: MySQL 8.x (17 tables)
  - Frontend: HTML5, CSS3, Vanilla JavaScript (no SPA framework)
  - Maps:     Leaflet.js 1.9.4 + OpenStreetMap / Nominatim reverse geocoding
  - Distance: Haversine formula (custom Location helper)
  - Charts:   Chart.js 4.4.7 (owner/admin analytics)
  - Auth:     Email/password (bcrypt) + Google OAuth (One Tap)
  - Note:     OSRM turn-by-turn routing is NOT implemented — search is
              distance-based only (Haversine), not route-based.

--------------------------------------------------------------------------------
2. CORE FEATURES
--------------------------------------------------------------------------------

Role-based dashboards:
  Three separate dashboards (driver / owner / admin), each with its own
  sidebar, role-scoped styling, and data scoping. Drivers see only their own
  bookings; owners see only their stations; admins see everything.

Station discovery — map + list, real-time availability:
  The landing page and driver dashboard show stations on a Leaflet map with a
  searchable, sortable list. The public /api/nearby-stations.php endpoint
  returns only approved, active stations with live "available chargers" counts
  derived from current booking/charging state — no sensitive internal fields.

Two-step booking flow:
  1. RESERVATION — driver picks a charger and pays a flat reservation fee
     (BOOKING_BASE_FEE). Booking moves to "booked" with an arrival deadline.
  2. CHARGING — when the driver arrives, they enter their current battery %,
     get a cost quote, confirm, and the session starts. The charging fee is
     calculated from battery-% × car capacity × per-kWh rate, and is billed
     as a SEPARATE transaction from the reservation fee.

Live countdown timers:
  Driver dashboard polls every 12 seconds while a session is active and shows
  live M:SS countdowns — "Arrive in M:SS" for the reservation window and
  "Ends in M:SS" for the charging session.

Stop-charging option:
  Drivers can stop an active session early. It's marked "stopped" (distinct
  from "completed") and the UI clearly warns NO REFUND.

OTP email verification for registration:
  New registrations require a 6-digit OTP sent to a @gmail.com address.
  OTPs are hashed (bcrypt), expire after 10 minutes, and are limited to a
  max number of attempts. Already-registered emails are rejected.

Notifications system:
  Built on the activity_logs table. Plain-text messages are written for
  session start, session stop, and booking expiry, and rendered in each
  role's notifications page.

Auto-reconciliation (SessionTicker):
  A lazy background tick runs on every booking API call and:
    - Auto-cancels bookings past their arrival deadline (with driver
      notification)
    - Recovers orphaned chargers stuck in "charging" with no active booking
      for over 6 hours
    - Auto-completes overdue charging sessions, calculates kWh/cost, releases
      the charger, and updates station stats — all race-safe with guarded
      UPDATEs.

--------------------------------------------------------------------------------
3. TECHNICAL HIGHLIGHTS WORTH PRESENTING
--------------------------------------------------------------------------------

Real Haversine-based nearby search:
  /api/nearby-stations.php pre-filters with a SQL bounding box, then applies
  the precise Haversine formula to compute exact distances and sort by
  proximity. Fast and accurate.

Two-payment transaction model:
  A single booking produces up to two payment_transactions rows — one for the
  flat reservation fee, one for the battery-% based charging fee — with
  distinct transaction IDs. This cleanly separates "reservation" from "usage"
  and keeps financial reporting consistent (filter on payment_status =
  'completed').

Automated background reconciliation:
  SessionTicker piggybacks on API traffic (no cron needed on XAMPP) and
  self-heals the system: expired bookings cancel themselves, orphaned
  chargers recover, and overdue sessions complete with correct billing.

Public API designed to avoid leaking internals:
  The public nearby-stations endpoint deliberately returns only non-sensitive
  fields (name, address, lat/lng, availability, rating) — never owner details,
  admin fields, or revenue.

--------------------------------------------------------------------------------
4. KNOWN LIMITATIONS (HONEST — "NEXT STEPS")
--------------------------------------------------------------------------------

Payment is simulated, not a real gateway:
  "Payment confirmation" currently generates a fake transaction ID and marks
  it completed — no money actually moves. Razorpay fields exist in the schema
  but are not wired up. This is the #1 blocker for production.

Open audit items (future work):
  - Booking queue race condition — the charger double-booking check is not
    row-locked (SELECT ... FOR UPDATE), so concurrent requests could exceed
    the 2-booking cap.
  - No CSRF protection on state-changing endpoints.
  - No rate limiting / brute-force protection on login.
  - kWh billing assumes every session charges to 100% (no end-battery input).
  - Google OAuth auto-approves new owner accounts (bypasses admin moderation).
  - Cascade-delete on stations destroys financial history (no soft-delete).

These are framed as "next steps" / "future work" — the app is further along
than a prototype but not yet production-ready.

5. ARCHITECTURE SUMMARY
--------------------------------------------------------------------------------

  d:/Xampp/htdocs/EE/
  │
  ├── app/
  │   ├── config/config.php        # Constants, DB singleton, helpers
  │   ├── helpers/
  │   │   ├── Auth.php             # Sessions, login/logout, role guards
  │   │   ├── Location.php         # Haversine distance calculation
  │   │   ├── SessionTicker.php    # Auto-reconciliation engine
  │   │   └── Mailer.php           # OTP email sending
  │   └── logs/                    # Application log output
  │
  ├── api/
  │   ├── auth/                    # login, register, logout, google, otp
  │   ├── bookings.php             # Full booking lifecycle + payments
  │   ├── stations.php             # Station/charger CRUD + admin moderation
  │   ├── nearby-stations.php      # Public, no-auth station discovery
  │   └── stats.php                # Platform statistics
  │
  ├── database/schema.sql          # 17 tables + sample data
  │
  ├── public/
  │   ├── index.php                # Landing page (role cards, map)
  │   ├── login.php / register.php # Auth pages (OTP + Google)
  │   ├── assets/                  # CSS + JS (dashboard.css, modal.js, etc.)
  │   └── dashboard/
  │       ├── driver.php           # Driver shell (map, booking modal, polling)
  │       ├── owner.php            # Owner shell (station mgmt, charts)
  │       ├── admin.php            # Admin shell (moderation, users)
  │       ├── sections/            # Driver sub-pages (AJAX-loaded)
  │       ├── owner_sections/      # Owner sub-pages (AJAX-loaded)
  │       └── admin_sections/      # Admin sub-pages (AJAX-loaded)
  │
  └── tests/integration_test.php   # Integration test suite

Key architectural points:
  - Vanilla PHP, no framework — simple require_once autoloading.
  - Server-rendered PHP pages with AJAX partial loads for dashboard sections.
  - Role-scoped body classes (role-admin / role-owner / role-driver) keep
    CSS/JS isolated per role.
  - All state-changing API endpoints enforce authentication + role guards.
